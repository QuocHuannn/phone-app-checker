# phone-app-checker reference

Detailed reference for the CLI. The [project README](../README.md) has the overview and quick start; this page documents behaviour, configuration, data handling and limits in depth.

Input: a CSV of phone numbers of people who agreed to be checked. Output: `report.csv`, one row per number, one status column per app (Telegram, WhatsApp, Zalo, Viber, LINE, Threema, Matrix), plus a summary table in the terminal.

Everything runs on your machine with **dedicated, disposable accounts**. Telegram, WhatsApp, Zalo, LINE and Viber are reached through open-source unofficial clients (or, for Viber, the real app); Threema and Matrix use their official lookup interfaces. Nothing is sent to a third party except the lookups the apps themselves make. **A Threema or Matrix lookup sends a hash of the number to the operator** (Threema Gateway, or your Matrix identity server); Threema's hash key is public, so the number is effectively disclosed.

> **Read this first.** The Telegram, WhatsApp, Zalo, LINE and Viber adapters drive an app in a way its terms of service do not allow, and the Threema and Matrix terms still apply to you. Checking accounts can be throttled, restricted or banned (you accept this risk by using the tool). Use dedicated accounts you can afford to lose, never a personal or business-critical number. Only check numbers of people who agreed to it: the tool does not check consent for you. See [responsible-use.md](responsible-use.md).

## Download for macOS (no Node.js needed)

Apple Silicon Macs (macOS 13.5 or newer) can run a prebuilt archive, `phone-app-checker-<version>-macos-arm64.tar.gz`, that carries its own Node.js runtime, precompiled JavaScript and dependencies. Verify the `.sha256`, unpack, run `bash install.sh`, open a new Terminal and type `phone-app-checker` with no arguments: a menu (English by default; press `L` to switch to Vietnamese, Indonesian, Malay, Korean or Simplified Chinese) walks through login, checking a CSV, accounts, the latest report, run history and Settings (see [Interactive menu](#interactive-menu)); the commands `phone-app-checker doctor` / `login` / `check` work as before (`doctor` is a command only, no longer a menu item). Step-by-step guide for non-developers: [install-macos.md](install-macos.md) (Vietnamese: [install-macos.vi.md](install-macos.vi.md)). Data, config and sessions live in `~/Library/Application Support/phone-app-checker`, never inside the program folder; keep customer CSVs in a dedicated local, non-synced folder (not `Documents`/`Desktop`/iCloud). The archive is built from this repository with `npm run release:build` (see [Development](#development)); the live-account checks listed under [What is verified, and what is not](#what-is-verified-and-what-is-not) still apply. The 13.5 floor is set by the bundled Node.js; the build and `release:verify` check every shipped Mach-O's minimum-OS load command, which is necessary but **not** a run on macOS 13.5 (only macOS 27 has run it). **Upgrading:** the first run upgrades your config in place (a 0.1.0 database is upgraded too); see [Config version and migration](#config-version-and-migration).

## What it never does

No messages, calls, friend requests or group invites. It does not read or store names, avatars, user ids, last-seen or any profile data (Telegram's client library would cache the profiles it receives; the adapter disables that cache and scrubs sessions written by older versions). Logs show phone numbers masked (`+8490****567`), also inside URLs and file paths. The only place full numbers are stored is the local SQLite file and the report you asked for.

## Status values

| Value | Meaning |
| --- | --- |
| `yes` | The app answered that the number has an account. |
| `not_found` | The app did not return an account for the number. **Not proof the person has no account**: users can hide themselves from search by phone number (Telegram, Zalo, LINE), and Viber's answer depends on contact sync. |
| `unknown` | Not checked yet, or the check failed / was throttled. Re-run `check`; unknown results are retried. |
| `skipped` | App disabled or not selected (`--apps`), or the number is outside the app's scope (Zalo only checks `+84`). |
| `invalid` | The cell is not a valid phone number (after normalisation with `defaultRegion`). Written for every app column. |

Report columns: `input` (your original cell), `e164`, `country`, `telegram`, `whatsapp`, `zalo`, `viber`, `line`, `threema`, `matrix`, `last_checked_at` (the newest time of **any** stored result for that number, an `unknown` attempt included, ISO-8601 UTC; empty for `invalid` rows; it says nothing about an individual app), then fourteen columns appended at the end: `<app>_checked_at` for the seven apps (when that app's `yes`/`not_found` itself was obtained; empty for `unknown`/`skipped`/`invalid`) and `<app>_stale` for the seven apps (`yes` when that `yes`/`not_found` is older than the max age or dated in the future, `no` when current, empty otherwise). The app columns follow the order of the app list, so read the report by header name, not by position. A `yes` or `not_found` is an observation at that time, not proof of identity or of a currently active account. A report written with an older header (0.1.0's five apps) is still recognised as this tool's own and overwritten without `--force`.

## Requirements

- Node.js **>= 22.18** (the CLI runs the TypeScript sources directly; `node:sqlite` is built in). Tested on Node 24.14 and 22.18.0.
- npm (the LINE client comes from the JSR registry; `.npmrc` already points `@jsr` at `https://npm.jsr.io`). `package.json` `overrides` pins `thrift` (used by the LINE client) to `^0.25.0` because 0.20.0 has published high-severity advisories; `npm audit --omit=dev` is clean with it.
- Per app, see [Per-app prerequisites](#per-app-prerequisites-and-limits).
- **Using the macOS download instead?** No Node.js or npm is needed: see [Download for macOS](#download-for-macos-no-nodejs-needed). The two requirements above apply only to running from source.

## Install

```sh
git clone https://github.com/QuocHuannn/phone-app-checker.git phone-app-checker && cd phone-app-checker
npm install
cp checker.config.example.json checker.config.json     # then edit; checker.config.json is git-ignored
```

Run the CLI as any of:

```sh
npm run cli -- <command>          # used in all examples below
./bin/phone-app-checker.js <command>
npm link && phone-app-checker <command>
```

`npm run cli -- --help` and `npm run cli -- <command> --help` list every option.

## Interactive menu

Run `phone-app-checker` (or `npm run cli`) **with no arguments in a terminal** to open a numbered menu, so nobody has to remember subcommands: 1 check a CSV, 2 log an account in, 3 `accounts`, 4 rebuild the latest report (`report`), 5 run history, 6 the guide and warnings (consent, `not_found` may mean privacy-hidden or not linked, LINE only in HK/JP/KR/TW/TH, Zalo Vietnam only, ban risk), 7 Settings (theme, language, recent files, paths), L change the language, 0 quit. `doctor` is no longer a menu item — run the command. Each action runs the ordinary command, so locks and the install/uninstall exclusion are taken and released per action; a command that fails shows its message, says that nothing was saved, and the menu stays open. Ctrl+C or Ctrl+D quits cleanly.

- **One back key.** `b` goes back on every prompt (Esc and `q` do the same in lists); Enter takes the default shown in the prompt. `b` is therefore reserved and cannot be an account name.
- **Check a CSV.** Drag the file from Finder into the window (quoted, backslash-escaped, `file://` and `~` paths are understood) or pick one of the **last 5 files** used. The list is `recent-files.json` in the data folder (mode 600; entries whose file is gone are kept but marked missing). `c` in the picker clears it and **stops remembering** — a permanent opt-out, not per session; deleting `recent-files.json` re-enables it. A **preview** then shows the detected phone column (read locally, nothing is sent), the row count, usable and unusable numbers with an example, and the countries, and asks you to confirm or go back. An app checklist follows (`Space` ticks, Enter starts; a numbered prompt in the plain tier), then the report path (default `report.csv` next to the CSV; the menu asks before overwriting).
- **Log in.** Lists the apps with their status, then asks how: WhatsApp = scan a QR code *or* a pairing code with the account's phone number; Telegram = QR *or* phone number + login code, after asking once for the `api_id` / `api_hash` and saving them in the config; Threema asks for the Gateway ID and a hidden secret; Matrix asks for the homeserver, user name and a hidden password. See [Login screens](#login-screens-qr-codes-pairing-codes-telegram-credentials). **Before a QR login the menu checks the window**: if the code does not fit it says how many columns x rows are needed (for example 68 x 39 for WhatsApp in colour) and waits for you to enlarge the window and press Enter, or offers the pairing code (`c`).
- **Accounts.** The list shows each account's state; `r` resets a cooling-down or disabled account, `l` goes to login.
- **After a run.** Enter returns to the menu; `o` reveals the report in Finder.
- **Run history.** Item 5 lists the last 20 `check` runs, newest first. Enter re-draws that run's summary (re-read from its report file, so it reflects the report's current contents) and `o` reveals the report; when the report is gone the row says so and the run's log is offered instead. Runs are recorded in `runs.json` in the data folder (mode 600, written atomically).
- **Settings.** Item 7 opens rows for the theme (auto / dark / light / high-contrast), the language (same list as `L`), clearing and stopping recent files, and the read-only config and data paths. The theme is saved to `checker.config.json` (mode 600, atomic) and the language to `menu-language` (mode 600) when there is an app home; a failed save — or a source checkout, where there is none — keeps the choice for the session only and says so.
- **First run.** When no account is logged in and the data folder has no `checker.db` yet, a one-time welcome box points at the guide; `welcomed.json` in the data folder suppresses it afterwards.

**Language.** The menu is in **English by default**, whatever the system locale. Every menu screen has an `L` line (`L. Language / Ngôn ngữ / Bahasa / 언어 / 语言: English`); `L` lists the languages, each in its own script, and switches at once:

| Code | Language | Status |
| --- | --- | --- |
| `en` | English (default) | source text |
| `vi` | Tiếng Việt | the original menu text |
| `id` | Bahasa Indonesia | first-draft, machine-quality; needs native-speaker review |
| `ms` | Bahasa Melayu | first-draft, machine-quality; needs native-speaker review |
| `ko` | 한국어 | first-draft, machine-quality; needs native-speaker review |
| `zh` | 简体中文 | first-draft, machine-quality; needs native-speaker review |

Menu prompts, guidance and warnings, the screens of `login` (QR/pairing-code instructions, Telegram prompts), the run dashboard and summary, and the messages of `check`, `report` and `accounts` are translated; the fix hints of `doctor` and its footer stay English. `login` takes the language from the menu, from `--lang <code>` (hidden flag of the `login` command), then `PHONE_APP_CHECKER_LANG`, then the saved choice, then English. Precedence for the menu itself: `phone-app-checker --lang <code>` (hidden flag, opens the menu in that language; only valid on its own) > environment variable `PHONE_APP_CHECKER_LANG=<code>` > the saved choice > English. A set but unsupported flag or variable value (anything other than the six codes above, any case) gives English, silently; an empty one counts as unset. The saved choice is the file `menu-language` (just the code, mode 600, written atomically) in the app home (`~/Library/Application Support/phone-app-checker`), validated like the config before it is written; it is removed by `uninstall.sh --purge-data` together with the rest of that folder. A language file that is missing, a symlink, oversized, owned by someone else, or readable/writable by group or others is ignored (English), and a failed save only means the choice lasts for that session (the menu says so and carries on). In a source checkout (no `PHONE_APP_CHECKER_HOME`) there is no private app home, so a switch lasts for the session only; use `--lang` or the variable there. Messages live in `src/i18n/`: one typed catalog per language, checked at compile time (`satisfies Catalog`) and by `tests/i18n.test.ts` (identical keys, identical placeholders, no empty strings, no control characters). Non-English catalogs are loaded on first use. Menu lines are wrapped to the window, never padded with spaces for alignment, because Korean and Chinese characters have no fixed width. **Translations other than English and Vietnamese are first drafts and have not been reviewed by native speakers.**

The menu opens only when there are no arguments **and** both stdin and stdout are terminals. With any subcommand, or when piped / run from a script, behaviour is unchanged (no arguments and no terminal still prints the usage and exits 1; the menu never waits for input there).

### Terminal UI (colours, arrow keys, progress bar)

Three output tiers, chosen once at start:

| Tier | When | What it does |
| --- | --- | --- |
| rich | stdout is a TTY, `TERM` is set and not `dumb`, no `NO_COLOR`, no `--plain` | colour, arrow-key lists, spinners, the live dashboard |
| lines | a TTY without those features | numbered prompts, plain progress lines |
| plain | `--plain`, `PHONE_APP_CHECKER_PLAIN=1`, `NO_COLOR`, `TERM=dumb`, an unset `TERM`, or output that is not a terminal | no colour, no cursor movement, no raw keys, ASCII icons; timestamped `HH:MM` lines while a run is going |

Everywhere outside the rich tier nothing writes an ANSI escape sequence. `--plain` is a global flag and sets the same mode as `PHONE_APP_CHECKER_PLAIN=1`, also for the menu. The UI layer is `src/ui.ts`, `src/select.ts`, `src/progress.ts`, `src/screens.ts` (hand-written ANSI; no UI dependency).

- **Banner.** A box with the app name, the version and a status strip of accounts ready per app (`✔ telegram 1 account`, `○ zalo none`). Icons are single-width (`✔`, `○`, `●` working, `◷` resting) with ASCII fallbacks (`[ok]`, `[ ]`, `*`, `~`); there is no emoji. `◷` means resting only — a cooldown or a wait with a known resume time; a plainly waiting account shows `○`. Boxes have a left bar only, no right edge, so Hangul / CJK can never push a border out of line; text is wrapped to the window and long paths are cut from the left (`…/Customers/report.csv`).
- **Arrow-key menus.** `↑` / `↓` + Enter, a row's own key (`1`-`7`, `L`, `0`) picks it at once, `b` / `q` / Esc go back (or quit from the main menu), Ctrl+C says goodbye. Every list draws a persistent hint line naming its keys (`↑↓ move · Enter select · Esc, q or b back`; the main menu's is `↑↓ move · Enter select · q quit · 1-7, L, 0`). Lists scroll when the window is short (they stay usable at 40 x 8). Used for the main menu, the file picker, the app checklist (`selectMany`), the method question, the language list, history and Settings. If raw mode is not available the classic numbered prompt is used instead. The terminal (raw mode, hidden cursor) is restored on a pick, on `b` / `q` / Esc / Ctrl+C / Ctrl+D, on any error, on `SIGINT` / `SIGTERM` / `SIGHUP` and on exit.
- **Login steps.** Every login shows `Step N/M - ...` headers (two steps for most apps; Telegram has its own three, below). Waiting states (`Connecting to Telegram...`, `Waiting for you to scan the code...`) are animated spinners on a terminal and never write anything to a pipe or a log.
- **Run dashboard.** On the rich tier `check` shows one framed panel: a title (`Checking customers.csv · 4 numbers`), `Elapsed · rate/min · ETA with the finish time`, one row per account (`APP ACCOUNT STATE DONE RESULTS LAST`: state `● working` green, `○ waiting` dim, `◷ resting` yellow with the local time it resumes, `✖ disabled` red with the reason, or `✔ done` bold green; per-status counts such as `0y 4nf 0u`; the last batch time) with a legend line (`● working  ○ waiting  ◷ cooldown  ✖ disabled  ✔ done`) under the rows, a totals bar (`28% 2 of 7 checks (4 numbers x 2 apps)`), the status counts, the `Ctrl+C finishes this batch and saves the report.` hint and the path of the run log. `◷` is resting only (cooldown or a timed wait); a plainly waiting account is `○`, and in the collapsed per-app view an app that is only pacing stays dim — only a real cooldown turns it yellow. It redraws at most once a second, collapses to per-app rows and then to totals on short windows, drops the RESULTS and LAST columns below 60 columns, and clamps every row to the window. The numbers come from the scheduler's progress events (one row per account); nothing is printed about customer numbers. The frame is erased before the summary is printed. Times are in local time (`14:05`, or `09 Oct 14:05` on another day). `--progress lines` writes plain `progress 40% 80/200 | telegram 50/100, zalo 30/100 | ETA 3 min` lines through the log instead (for logs; at most one every 10 s), `--progress off` nothing extra, default `auto` = the dashboard on a rich terminal and **nothing extra anywhere else**. The lines and plain tiers print the labelled header and the legend once before the first progress line; in the plain tier state changes are printed at once and progress at most every 10 s, each line prefixed with the local `HH:MM`.
- **Run log.** Every `check` writes `check-<timestamp>.log` in the data folder (mode 600, masked numbers); the 5 newest are kept. In the dashboard the per-batch lines go to this file only; on the lines and plain tiers they are printed.
- **Results.** The summary starts with `Done in 3 s · 4 numbers · 0 unfinished`, then the status table (coloured on a terminal: `yes` green, `not_found` yellow, `invalid` red, `unknown` / `skipped` and zero counts dim) whose per-app cells show `N (P%)` — the count and its share of the input rows — a bold `TOTAL` line summing each status over all shown app-cells (numbers x apps), and a country table (top 10) whose `total` column is every shown app-cell and whose `yes` and `%` are shares of that whole, **not** a within-country success rate (per-country row counts do not exist). Then `Accounts used: telegram a · zalo z` and a `Report saved to <path>` box with the next steps (open the file with Excel / Numbers; `o` in the menu, or `open -R '<path>'`, shows it in Finder); an **INCOMPLETE** run adds a bold red warning. Only the standard 8-colour palette plus bold / faint / reverse is used (no white, black or bright-black text), which stays legible on light and dark themes; the accent colour follows `theme` (cyan on dark, blue on light, bold + inverse on high-contrast). This was chosen, not measured on screen.
- **Theme.** `theme` in the config and the `--theme` flag take `auto` (the default; detects the terminal background from `COLORFGBG` — the last number's colour class decides, bright means light — and falls back to dark), `dark`, `light` or `high-contrast`. The accent colour follows: cyan on dark, blue on light, bold + inverse on high-contrast. Precedence: `--theme <mode>` > `theme` in `checker.config.json` > `auto`; menu item 7 toggles it and saves the choice (mode 600) when there is an app home — session-only otherwise. The theme only affects the rich tier: `--plain` / `NO_COLOR` output is identical either way. Implementation: `resolveTheme` in `src/ui.ts`.
- **Telegram in three steps.** Choosing Telegram first shows `Step 1/3 Get your free Telegram API keys (one-time)`, `Step 2/3 Save the keys`, `Step 3/3 Scan the QR code (or enter phone + code)` and **why**: Telegram requires an `api_id` / `api_hash` from every program that logs in, and the QR code appears in Step 3, right after the keys are saved. If the keys are already in the config (or the environment) it says `API keys found` and goes straight to Step 3. Step 1 prints `https://my.telegram.org/apps`, says what to type in the form (App title and Short name: anything; Platform: Other) and, **only on a terminal, only for that one fixed address, and only after you answer yes** (`[y/N]`, default no), opens it with macOS `open` (no shell). Step 2 asks for the `api_id` (digits) and the `api_hash` (32 hex characters, shown as one mask character per key, never the value), with friendly messages for the usual mistakes (api_hash typed as api_id and the reverse, wrong length); `b` goes back at any of those questions. After a QR scan the screen names the linked account (display name and a **masked** phone number, never the session).
- **Telegram refusals in plain words.** `FLOOD_WAIT_n` (how long to wait), `PHONE_MIGRATE`, `SESSION_PASSWORD_NEEDED`, wrong phone / code / expired code / wrong two-step password, `API_ID_INVALID`, banned or blocked number, too many attempts, and any other Telegram error code (quoted) are translated into one sentence each, in the login language.
- **No shared API keys.** Telegram requires each operator's own `api_id` / `api_hash` (a shared pair would break Telegram's rules and risks getting accounts banned), so the tool never ships one.

## Configure

`checker.config.json` is optional; every key falls back to the built-in default. Unknown keys are rejected so typos fail loudly. [`checker.config.example.json`](../checker.config.example.json) contains every key with its default.

| Key | Default | Meaning |
| --- | --- | --- |
| `configVersion` | `3` | Written by the tool. A file without it is a 0.1.0 file and is upgraded automatically (see [Config version and migration](#config-version-and-migration)); a file with a newer number than this build knows is refused untouched. |
| `defaultRegion` | `"VN"` | Country used for numbers written without a country code (`0901234567`). ISO-3166 alpha-2, upper case, and a real country (`GB`, not `UK`): an unknown code would mark every national number invalid, so it is refused. |
| `dataDir` | `"./data"` | Sessions (secrets!), SQLite results. |
| `maxAgeDays` | `30` | `yes` / `not_found` younger than this are reused, not re-checked. |
| `theme` | `"auto"` | Rich-tier colour theme: `auto`, `dark`, `light` or `high-contrast` (see [Terminal UI](#terminal-ui-colours-arrow-keys-progress-bar)). `--theme` overrides it for one run; menu item 7 saves it when there is an app home. |
| `apps.<app>.enabled` | telegram/whatsapp/zalo `true`; viber/line/threema/matrix `false` | Apps checked when `--apps` is not given. |
| `apps.<app>.batchSize` | 10 / 20 / 1 / 100 / 1 / 1 / 1 | Numbers per call (whole number, at least 1), in the order telegram / whatsapp / zalo / viber / line / threema / matrix. |
| `apps.<app>.dailyCap` | 200 / 300 / 100 / 1000 / 50 / 100 / 100 | Numbers per account per local day (whole number, at least 1), same order. |
| `apps.<app>.minIntervalMs`, `jitterMs` | see example | Pause between two batches on one account (`min + random(0..jitter)`). Every duration setting is in milliseconds and at most one year, so an extra zero fails loudly instead of hanging a run. |
| `apps.<app>.rateLimitCooldownMs` | 6 h / 6 h / 24 h / 12 h / 24 h / 1 h / 6 h | Rest after a throttle without explicit wait time, same order. |
| `apps.<app>.errorCooldownMs` | 10 min | Rest after an unexpected error. An account failing 3 batches in a row is dropped for the rest of the run. |
| `apps.<app>.maxParallelAccounts` | `1` | How many accounts of this app may have a batch in flight at once (whole number, at least 1). `1` is the 0.1.0 behaviour. Viber is always one (a single device) and a higher value is refused. |
| `apps.<app>.options` | | App-specific settings, below. |

Defaults are conservative guesses: platforms do not publish limits (the Threema and Matrix values are guesses too, written without a live trial). Tune them with a small pilot run of your own. **Throughput = number of accounts x `dailyCap` per day**: 10 000 numbers on one Telegram account at the default `dailyCap` of 200 takes 50 days, so plan for several accounts or a higher, tested cap.

**Parallel accounts.** `maxParallelAccounts` above 1 only helps when a batch takes long compared with the pause between batches: with quick batches the run is bound by pacing and extra parallelism gains nothing (simulation in [performance.md](performance.md#parallel-accounts)). `accounts` shows each account's average and last batch time; measure first, raise one step at a time, and remember that more simultaneous sessions raise the ban exposure. The daily cap is reserved when a batch is sent, so it is never exceeded.

### Config version and migration

`configVersion` is `3` in 0.3.0 (2 added it in 0.2.0; 3 adds `theme`). A file without it is the 0.1.0 format and upgrades through both steps. The first time 0.3.0 reads an older file it validates the upgraded content, writes a mode-600 backup created exclusively — `checker.config.json.v2.bak` for a 0.2.0 file, `checker.config.json.v1.bak` for a 0.1.0 one; an existing backup is never overwritten, a numbered `.v2-2.bak` is added — replaces the config atomically (mode 600) and prints one line on stderr naming the backup. Running again changes nothing. Unknown keys are still rejected, and a file with a newer `configVersion` than this build knows is refused untouched (`the config file needs a newer version of this program (configVersion N, supported 3)`). `saveTelegramCredentials` (the menu's key entry) and the Settings theme save run the same in-memory migration but write the upgraded file **without** a `.v<N>.bak` backup — a silent upgrade; the rollback path below only exists after a `loadConfig` read (any `doctor`/`check`/menu start). The upgrade is **one way**: 0.2.0 refuses a version-3 file for the same reason. To go back, install the older build and copy the `.v<N>.bak` over `checker.config.json` (a 0.1.0 restore also needs a copy of `checker.db` made before that upgrade — see [Data and secrets](#data-and-secrets)).

## Log in (once per account)

Each account is a directory `data/sessions/<app>/<account>`; every directory counts as one account for that app. Use several accounts per app to spread the load.

```sh
export TELEGRAM_API_ID=1234567 TELEGRAM_API_HASH=0123456789abcdef0123456789abcdef   # or set in the config
npm run cli -- login telegram --account tg1                      # phone number, login code (hidden), 2FA password (hidden)
npm run cli -- login telegram --account tg1 --method qr          # QR code: Telegram > Settings > Devices > Link Desktop Device
npm run cli -- login whatsapp --account wa1                      # QR -> Linked devices on the phone
npm run cli -- login whatsapp --account wa1 --method code --phone +84901234567   # 8-character pairing code instead of a QR
npm run cli -- login zalo     --account z1                       # QR in the terminal, scan it in the Zalo app
npm run cli -- login viber    --account vb1    # only VERIFIES the emulator/phone setup, see docs
npm run cli -- login line     --account l1     # QR or e-mail/password + PIN on the phone
npm run cli -- login threema  --account th1                       # Gateway ID, then the secret (hidden); verified with a credits call
npm run cli -- login matrix   --account mx1                       # homeserver, user name, password (hidden) -> identity-server token
```

Account names: 1-32 letters, digits, `-`, `_`. Re-running `login` for the same account refreshes its session and clears its cooldown/disabled flag. A first login that fails or is interrupted (Ctrl-C/SIGTERM) removes the half-created directory and registers nothing; account state in the database is only touched after a successful login. Login output (QR codes, URLs, pairing codes) is printed verbatim; it never contains customer numbers. Everything else (scheduler logs, top-level errors) masks every phone-like digit run, including inside URLs and paths. A WhatsApp account whose directory holds no linked device (for example after a failed re-pair) is disabled with a `login whatsapp --account <name>` hint instead of being retried on every run.

The account name `b` is reserved (it means "back" in the menu). Threema and Matrix store `credentials.json` in the account directory; a failed login saves nothing and leaves an earlier working login as it was.

### Login screens: QR codes, pairing codes, Telegram credentials

- **One QR renderer for every app** (`src/qr.ts`). The code is drawn with *explicit* colours (pure black on pure white half blocks, white quiet zone of 4 modules, or 2 when the window is short), so it is the same on dark and light terminal themes and square on screen. Without colours (`NO_COLOR` set, `TERM=dumb`, output not a terminal, or a `CI` variable that Node reads as "no colour") it prints a plain `##` / blank version with a note: that one is only right on a light theme. If the window is too small the code is **not** drawn (a wrapped code cannot be scanned): a message gives the columns x rows needed (`Enlarge the window, or press Cmd+minus`), and the code appears by itself when the window is big enough. WhatsApp's current code is 61 modules (a 277-character link, measured on a live capture) and needs a window of about 72 x 39 (columns x rows; 68 x 37 with the smaller quiet zone): the default 80x24 Terminal window is too short for it, so expect the enlarge message there. When the service rotates the code (WhatsApp every ~20 s after the first one, Telegram every ~30 s, Zalo after ~100 s) the new one replaces the old one on a terminal and is marked `New QR code (#n)`; it is removed when the login ends.
- **Why the old picture did not scan.** The previous `qrcode-terminal` `small: true` picture used the terminal's own colours, a 1-module border (and none at the bottom for an odd size), and a WhatsApp code of 61 modules is 31+ rows, so it does not fit a default 24-row window. `tests/qr.test.ts` rasterises both outputs and decodes them with jsQR: the old one decodes only with ideal dark-theme colours (so a dark theme alone does not explain a failure: that was *measured*, not assumed) and is inverted on a light theme; the new one decodes on dark, light and hostile themes. That is a simulation, not a phone camera.
- **WhatsApp.** Menu option 1 = pairing code (recommended, default): the menu asks for the account's phone number (checked with the same normaliser as the CSV), `login --method code --phone <number>` asks Baileys for an 8-character code and prints it with *Link with phone number instead*. Option 2 = QR. A QR scan failed on a real iPhone ("check your connection and try again") because WhatsApp now sends `companion_reg_refresh` after a scan and Baileys 7.0.0-rc14 ignores it (WhiskeySockets/Baileys#2737); the adapter now answers it (new secret, same code redrawn) and uses the WhatsApp Web version WhatsApp serves instead of Baileys' bundled one. Not yet confirmed with a phone: see [docs/whatsapp-setup.md](whatsapp-setup.md). After a login the menu prints one success line and *Next step: choose 1*.
- **Zalo.** zca-js hands over the login QR only as a PNG (`data.image`; its `data.code` is a different, internal token). `src/qr-png.ts` reads the module grid back out of that picture (plain-PNG decoder on Node's `zlib`, no dependency; tolerates the rounded finder corners of Zalo's picture) and redraws it with the shared renderer, so no file is written. Only if the picture cannot be read does the adapter fall back to saving `login-qr.png` (mode 600, inside the account directory, deleted afterwards), printing its path and, on a macOS terminal, opening it.
- **Telegram.** Option 1 = QR login (`client.start({ qrCodeHandler })`: mtcute 0.32 supports it; every token Telegram issues is drawn, a two-step password is asked hidden after the scan, nobody scanning for 5 minutes ends the login), option 2 = phone number + login code. With no `--method` the command keeps asking for phone + code. The menu walks through the `api_id` / `api_hash` first when they are missing: see [Terminal UI](#terminal-ui-colours-arrow-keys-progress-bar) and [docs/telegram-setup.md](telegram-setup.md).
- **LINE** uses the same renderer for its QR URL.

Step-by-step guides with the exact prompts, risks and error meanings: [README.md](README.md).

## Check

```sh
npm run cli -- check customers.csv --out report.csv
```

- The phone column is auto-detected (header like `phone`, `SĐT`, `mobile`, ...; or the column whose cells parse as phone numbers). Force it with `--column phone` or `--column 3` (1-based). Delimiter `,` `;` or tab, line endings LF / CRLF / CR, a UTF-8 BOM and Excel's **Unicode Text** export (UTF-16 with BOM) are handled. A binary file such as an `.xlsx` workbook is refused with a hint to save as *CSV UTF-8*. Cells Excel turned into scientific notation (`8.49E+10`) lost their digits and are reported `invalid`, never guessed.
- Numbers are normalised to E.164, de-duplicated (first spelling is kept in the `input` column) and checked once per app.
- `--apps telegram,zalo` limits the run; other columns become `skipped`. `--max-age 7` reuses answers younger than 7 days (`0` re-checks everything); a result dated in the future is never reused, even with `--max-age 0` or a huge value. `report` accepts `--max-age` too (it only decides which cells are flagged stale).
- **Output file safety.** `--out` must not be the input CSV (also through a symlink or hard link) nor anything inside `dataDir`, however its letters are cased on a case-insensitive volume (macOS, Windows), even when the file does not exist yet. An existing `--out` is replaced only when it is a previous report of this tool (or empty); any other existing file needs `--force`. Cells that a spreadsheet would run as a formula (`=`, `+`, `-`, `@`, tab, CR or LF at the start, also in full-width form or after spaces) are written with a leading `'` in the `input` column. The report is written to a private temp file and renamed into place, so an interrupted run never leaves a half-written report; temp files of killed runs are removed by the next run once they are 15 minutes old.
- **One run at a time.** `data/check.lock` stops a second `check` from sharing accounts with a running one (a second WhatsApp connection would disable that account). `login` and `account-reset` take the same lock, so they refuse to run next to a `check` (or each other) instead of re-pairing or resetting an account that is in use; wait for the other command or, if its process is gone, delete the lock file. The lock is published atomically (private file + `link()`), and a stale lock (dead owner) is reclaimed under a separate guard `check.lock.reclaim`. A guard left by a process killed *during* that recovery is **never** broken automatically (breaking it cannot be made safe against a second reclaimer): the command stops with `Lock recovery was interrupted … Repair: … delete …` and a person removes the named file once no command is running. Non-`ENOENT` read errors on the lock (permissions, I/O) are surfaced, never treated as a stale owner. The lock trusts a pid on this host: use a local, non-synced data directory.
- **Lifecycle exclusion (install/uninstall vs commands).** `check`, `login`, `report`, `accounts`, `account-reset` and `doctor` register in `~/Library/Application Support/phone-app-checker-lifecycle/shared/<pid>.<token>` **before** the home is bootstrapped or any database opened. `install.sh` / `uninstall.sh` publish `maintenance.lock` there, hold it for their whole run (including the `DELETE` prompt and the copy) and then read the registrations; every command reads the barrier after registering, so neither side can miss the other. The directory is outside the app home, the install tree and any `dataDir`, so it also covers `--config`, an external `dataDir` and another `PHONE_APP_CHECKER_HOME`. Maintenance waits up to 3 s for registered commands (then refuses naming the pid); registrations of dead processes are ignored. A barrier left by a killed install/uninstall fails everything closed with `An earlier install or uninstall … was interrupted … delete …maintenance.lock` and is never broken automatically. Every refusal (barrier, registration, run lock, reclaim guard) names the exact file and says `if nothing is running, delete <file>`: after a crash or power cut the recorded pid may have been reused by an unrelated process, and a pid that exists but cannot be signalled (EPERM) counts as alive in both Node and the shell scripts, so the check fails closed. The hidden `data-dir` command is exempt (the scripts call it while holding the barrier).
- Results are committed to SQLite after every batch. **Ctrl-C (or SIGTERM) stops dispatching, finishes the batch in flight, writes the report and exits 130**; a second Ctrl-C quits immediately. With `maxParallelAccounts` above 1, batches in flight get 30 s to return and commit; any that do not are abandoned, their numbers stay `unknown` and are charged to the daily cap, so a rerun repeats at most that many batches. Running again continues where it stopped; numbers with a fresh answer are not asked again. A re-check that gets no answer never overwrites an earlier `yes` / `not_found`: the old answer stays, **but it is not re-confirmed**: its own time is in `<app>_checked_at` and `<app>_stale` flags it once it is older than the max age (`last_checked_at` is the newest time across all apps and attempts, so it can look recent while one app's answer is old). SIGKILL cannot be handled: results committed before it are kept, but the in-flight batch may be asked again and Telegram's imported contact or Viber's injected contacts may not have been cleaned up (Telegram's cleanup is best effort; Viber removes leftovers at the start of the next batch). Use one Ctrl-C and wait for the report. A sleeping laptop suspends the run until it wakes.
- A batch that keeps failing with an unexpected error although this run already got answers (e.g. one number a platform rejects) is retried, then parked after two failures and left `unknown` for this run, even when it is the last batch left. No account is put on cooldown for it (cooldowns its failures caused are lifted) and parked failures do not count towards dropping an account (three other failures in a row do). With no success yet in the run, repeated failures are treated as an outage: the account is dropped for the run after three in a row (not banned: usable again next run). Numbers from a failed batch are remembered in the database until they are answered; the next run checks them **last and one by one**, so the healthy numbers that shared a batch with a rejected one get their answer, and a few rejected numbers at the top of the list cannot stop everything behind them.
- When every account is cooling down or at its daily cap, `check` sleeps until one is available, which can mean days for big lists. Run it somewhere that will not sleep (`caffeinate -i npm run cli -- check ...`, `tmux`), or pass `--no-wait` to stop instead and re-run later (cron).
- **Progress.** On a terminal the run dashboard is drawn in place (see [Terminal UI](#terminal-ui-colours-arrow-keys-progress-bar)); `--progress lines|off|auto` chooses plain lines, nothing, or the default, and `--plain` removes colour and cursor movement. Without a terminal the output is plain lines. Per-batch detail goes to the run log `check-<timestamp>.log` in the data folder (last 5 kept).
- **Run summary and INCOMPLETE banner.** Every app gets one line `needed N, attempted A, conclusive C, inconclusive I` with a reason (`no usable account`, cooldown, daily cap, errors, parked batches, unknown answers), and `(all conclusive)` replaces `(done)` only when nothing is inconclusive. If any number has no fresh `yes`/`not_found` from this run, a banner is printed **last** (after `Report written to …`): `INCOMPLETE: X of Y checks have no fresh yes/not_found answer. The report is NOT final …` with per-app reasons (`no_accounts`, `adapter_error`, `aborted`, cooldown, daily cap, …) and `Next resume: <ISO time>` when known (earliest across apps). Apps without any logged-in account are included (`no_accounts`; also logged as `no accounts ... Run: login <app>`) and stay `unknown`. Exit code stays `0` (`130` if interrupted): it means the command produced its output, **not** that every number was conclusively checked, so read the banner and the `<app>_stale` columns. A file with zero valid numbers is an error: `check` exits `1` with `no valid phone numbers (N invalid); check --column …` before the store is opened and writes no report.
- **Reading the summary.** A run ends with `Done in <time> · N numbers · U unfinished` (U = numbers still without a fresh answer), the per-app table whose cells are `N (P%)` where P is the share of input rows, a `TOTAL` line and a top-10 country table whose percentages are shares of all shown app-cells (not a within-country rate), `Accounts used: <app> <account> · ...` and the report path. `accounts` prints a batch-time column (average / last) per account, which is how you decide whether to raise `maxParallelAccounts`.

Monthly routine: put the new export through `check`; answers younger than `maxAgeDays` are reused, the rest are refreshed.

## Report only, accounts

```sh
npm run cli -- report customers.csv --out report.csv      # rebuild report.csv from stored results, no network
npm run cli -- accounts                                    # per account: ready / cooling down until ... / DISABLED: reason, used today
npm run cli -- account-reset telegram tg1                  # clear cooldown / disabled flag after you fixed the cause
```

`report` shows the last known answer even when older than `maxAgeDays`: such cells have `<app>_stale` = `yes` and the summary prints a `STALE:` line (use `--max-age <days>` to choose the threshold; a future-dated result is always stale). With zero valid numbers it still writes the report (only `invalid` rows), prints `WARNING: no valid phone numbers (N invalid)` and exits `1`, like `check`.

File modes are set to 600 by the adapters (Telegram `session.sqlite*`, LINE, Zalo, Viber state, QR image; WhatsApp files are set to 600 when a session closes). Never commit, share or put in a synced folder. |

Created mode 600 before SQLite opens it; mode of the database and its sidecars is repaired to 600 on open; symlinks are refused. Telegram's own session database stores no customer profiles (see [docs/telegram-setup.md](telegram-setup.md)). |
| `data/check.lock` | pid of a running `check`, `login` or `account-reset` | Removed on exit, SIGINT/SIGTERM/SIGHUP; a lock left by a dead process is reclaimed on the next run, **unless** its reclaim guard `data/check.lock.reclaim` was abandoned mid-recovery: then the run refuses until a person deletes that file (see "One run at a time" under Check). |
| `~/Library/Application Support/phone-app-checker-lifecycle/` | `shared/<pid>.<token>` registrations of running commands; `maintenance.lock` while install/uninstall runs | Outside home, install tree and `dataDir`; emptied by the uninstaller; an abandoned `maintenance.lock` fails closed until deleted by hand. |
| `~/Applications/phone-app-checker/.incoming.*`, `.replaced.*` | New copy being prepared / previous copy kept until the new `--version` self-check passes | Removed when the install finishes; a killed install leaves `.replaced.<version>.*`, which the next `install.sh` restores. |
| `report.csv`, input CSVs | Customer numbers | `report.csv` is written mode 600 through a private temp file and renamed into place; input CSVs keep their own mode. `*.csv` is git-ignored. |
| `data/check-<timestamp>.log` | The run log of a `check` (masked numbers) | Mode 600; the 5 newest are kept. |
| `recent-files.json` (data folder) | Paths of the last 5 CSV files picked in the menu; an entry whose file is gone is kept but marked missing | Mode 600; `c` in the file picker or the Settings row clears it and stops remembering permanently (delete the file to opt back in). |
| `runs.json` (data folder) | Run history: time, CSV, apps, rows, report and log paths of the last 20 `check` runs | Mode 600, written atomically; menu item 5 re-shows a run's summary by re-reading its report file (the entry follows the file, so a rebuilt report changes what an old entry shows). |
| `welcomed.json` (data folder) | Flag that the first-run welcome was shown once | Mode 600; delete it to see the box again. |
| `checker.config.json.v1.bak` / `.v2.bak` | Older configs kept by the upgrade (1 = 0.1.0 format, 2 = 0.2.0) | Mode 600, never overwritten (a numbered backup is added). Contains your settings and perhaps `api_hash`: treat it like the config. |

**Refused folders and purge rules.** The app home (`PHONE_APP_CHECKER_HOME`) and `dataDir` may not be `/`, the user's home or a parent of it, any of `Documents`, `Desktop`, `Downloads`, `Library`, `Applications`, `Movies`, `Music`, `Pictures`, `Public`, `.local`, `.config`, `Library/Application Support`, `.local/bin` (matched by inode and case-insensitively, so aliases and symlinks do not slip through, **even when a marker file exists**), nor overlap `~/Applications/phone-app-checker` (replaced on install, deleted on uninstall). Checked before anything is written. `uninstall.sh --purge-data` deletes a whole tree only when it is a real directory named `phone-app-checker`, owned by you, not overlapping the install tree, containing a real (non-symlink) `checker.config.json` or `data/checker.db`; custom or shared folders are refused even with `--yes` (delete what you created there by hand), and an absolute external `dataDir` is reported as retained, not deleted. The configured `dataDir` is read **before** anything is removed (from the installed copy, or from `checker.config.json` when the program is already gone, e.g. after an ordinary uninstall); if it is set but cannot be located with certainty, `--purge-data` refuses before the prompt and keeps the config. Anything other than `DELETE` at the prompt still uninstalls the program and keeps the data; delete the data later with `uninstall.sh --purge-data` from the downloaded bundle. Uninstall also removes `~/.zprofile`/`~/.bash_profile` again when the installer created the file and it is empty after its PATH block is removed. A plain uninstall refuses when the home or `dataDir` lies inside the install tree. Purge is local file deletion only: not a remote logout (unlink the devices first) and not secure erasure (backups and Time Machine snapshots may keep copies).

**Install activation.** `install.sh` holds the maintenance barrier, copies to `.incoming.<version>.<pid>`, moves the old copy of the same version to `.replaced.<version>.*`, activates, runs `--version`, and only then deletes the old copy; any failure (or an interruption caught by the EXIT trap) rolls back, a SIGKILL leaves the old copy for the next run to restore. `current` and `~/.local/bin/phone-app-checker` switch with an atomic rename, and shell profiles (also through a symlink) are rewritten beside the target and renamed over it. Rollback to an older retained version: `bash ~/Applications/phone-app-checker/<version>/install.sh`.

**Schema v3.** `data/checker.db` uses schema version 3 (`failed_checks` came with 2; 3 adds per-account batch times), migrated in place by explicit per-version steps. A database written by a newer schema cannot be opened by an older build (`Database was written by a newer version`; the version check runs before anything is changed), so **0.1.0 cannot open an upgraded database**: do not downgrade over existing data without a copy of `checker.db` made before the upgrade.

Delete `data/` and the CSVs when you no longer need them.

**Packaged app (macOS download).** When the command is started through the bundled `phone-app-checker` wrapper it sets `PHONE_APP_CHECKER_HOME`, and everything above moves out of the working directory: the config is `~/Library/Application Support/phone-app-checker/checker.config.json` (created from the example on first run) and `data/` is `~/Library/Application Support/phone-app-checker/data` (relative `dataDir` values are resolved against that folder). Input CSVs and `report.csv` stay in the current directory. With the variable unset (a source checkout) nothing changes.

## What is verified, and what is not

Automated (`npm test`, no accounts needed): CSV parsing and normalisation, config validation and migration, the scheduler and its per-app dispatcher (batching, caps, cooldowns, resume, Ctrl-C, parallel accounts on a virtual clock, parking a batch that keeps failing), SQLite persistence, its migrations and its file permissions, report/summary and its output-file safety, the run lock, the menu and dashboard on an emulated screen grid, the CLI end to end with a **test-only injected adapter**, the seven real adapters failing closed with setup hints when no credentials exist, and each real adapter's error classification (`yes`/`not_found`/rate-limit/ban/other) against test doubles of the third-party client (Telegram's real mtcute storage is exercised to prove no customer profile is persisted), including the Viber adapter against a simulated Android device with a real SQLite file and the Threema and Matrix adapters against stubbed HTTP responses. The suite passes on Node 24.14 and on Node 22.18.0 (the minimum in `engines`; run there from an install made with that Node, because `better-sqlite3`, used by mtcute, is a native module built per Node version). The release archive is checked by `npm run release:verify` (V1-V20, including an upgrade from a 0.1.0 home). Speed and memory numbers: [performance.md](performance.md).

**Live accounts.** Only WhatsApp has been exercised against the real service, by the maintainer: one account linked with a pairing code and a handful of lookups (a registered number returned `yes`, an unregistered one `not_found`). No known-answer trial of ~20 numbers has been done for any app. **Telegram, Zalo, Viber, LINE, Threema and Matrix have not been verified against the live platforms**, and the live-account pilot per app is still open. Not verifiable without credentials/devices:

- That each unofficial client still speaks the current Telegram / WhatsApp / Zalo / LINE protocol, including the exact error names/codes the adapters map to `rate limit` / `ban`.
- That `yes` / `not_found` match reality: run `check` on a ~20-number staff file with known answers per app and compare before trusting a customer run. A silent soft throttle on the platform side can look like `not_found`; the tool cannot detect it.
- Real rate limits and the throughput you can sustain without losing accounts.
- Viber: the DB schema and queries for your Viber version, root access, whether Viber activates on the emulator (fallback: a rooted phone), and that the device has `tar` for the single-archive database read.
- LINE: availability of phone search for your account's region.
- Threema: whether lookups use Gateway credits, whether the Gateway terms allow checking a customer list, and whether a Basic Gateway ID is enough.
- Matrix: which identity servers still answer phone lookups in 2026, whether `vector.im` accepts a new token for an account on another homeserver, and how many people have a phone number linked at all.

## Development

```sh
npm run typecheck     # tsc --noEmit
npm test              # vitest
npm run smoke         # end-to-end demo (login, check, resume, report) with a test-only adapter
npm run build         # compile src/ and bin/ to build/js/ (what the macOS archive runs)
npm run bench         # offline benchmark with fake adapters; see performance.md (also bench:startup)
npm run licenses:check   # fail if THIRD_PARTY_LICENSES.md is out of date (npm run licenses regenerates it)
npm run release:build    # macOS arm64 portable archive -> dist/ (needs network + Apple Silicon; see below)
npm run release:verify   # clean-room install/upgrade/uninstall check of the archive in dist/
```

`release:build` produces `dist/phone-app-checker-<version>-macos-arm64.tar.gz` plus a `.sha256`, bundling the pinned official Node.js build, the compiled JavaScript, the production `node_modules` built by that Node, and the install/uninstall scripts from `release/`. `release:verify` unpacks it in a temporary HOME without Node on `PATH` and exercises install, `doctor --deep`, offline `report`, reinstall, the upgrade from a 0.1.0 and a 0.2.0 home, and uninstall (V1-V20). Nothing is published or uploaded by these scripts; the `release` GitHub workflow builds and uploads the archive for tags. The tester's guide is [install-macos.md](install-macos.md) (shipped inside the archive as `INSTALL.md`, Vietnamese as `INSTALL.vi.md`), together with `LICENSE` and `THIRD_PARTY_LICENSES.…

Layout: `src/cli.ts` commands, `src/scheduler.ts` the per-app dispatcher, `src/store.ts` SQLite and its migrations, `src/adapters/<app>.ts` the seven real adapters behind `src/types.ts` (`Adapter`/`Session`), `src/android/adb.ts` adb wrapper for Viber, `src/menu.ts` / `src/ui.ts` / `src/progress.ts` the menu and dashboard. CLI/scheduler tests substitute adapters only through the `loadAdapter` seam of `createProgram`; adapter tests replace only the third-party client, `fetch` or `adb` with test doubles (`vi.mock`, `vi.stubGlobal`). There is no fake mode at runtime.
